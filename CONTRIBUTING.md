# Contributing to TOON Dataset Compiler

> **Building engineering intelligence is a collaborative effort. Every contribution should improve the quality, structure, and reasoning ability of the dataset.**

---

# Introduction

Thank you for contributing to the TOON Dataset Compiler.

Unlike traditional software projects, TOON is not simply a codebase.

It is an Engineering Knowledge Compiler.

Every contribution should improve one or more of the following:

- Engineering knowledge
- Reasoning quality
- Dataset quality
- Ontology completeness
- World realism
- Engineering accuracy
- Educational value
- Long-term maintainability

The objective is not to generate more data.

The objective is to generate better engineering knowledge.

---

# Philosophy

Every contribution should satisfy these principles.

1. Knowledge before quantity.
2. Engineering before programming.
3. Evidence before assumptions.
4. Reasoning before answers.
5. Graphs before flat text.
6. Reusability before duplication.
7. Quality before speed.
8. Simplicity before cleverness.
9. Explainability before complexity.
10. Continuous improvement.

# Contribution Workflow

Every contribution follows the same lifecycle.

```
Idea

↓

Discussion

↓

Specification

↓

Implementation

↓

Validation

↓

Review

↓

Merge

↓

Release
```

No step should be skipped.

Examples


---

# Commit Messages

Every commit should clearly describe its purpose.

Format

```
<type>: <description>
```

Examples

```
feat: add engineering ontology

fix: repair reasoning graph generation

docs: improve architecture documentation

refactor: simplify generation pipeline

test: add ontology validation
```

---

# Pull Requests

Every pull request should answer

- What problem does this solve?
- Why is this change necessary?
- Which compiler modules are affected?
- How was the change validated?
- Does this introduce breaking changes?

---

# Coding Standards

All code should be

- deterministic
- modular
- documented
- testable
- reproducible
- platform independent

Avoid

- hidden state
- duplicated logic
- unnecessary abstraction
- magic constants

---

# Documentation Standards

Documentation should

- explain intent
- explain reasoning
- define assumptions
- provide examples
- remain implementation independent where possible

Every specification should answer

- Why?
- What?
- How?
- Inputs
- Outputs
- Constraints
- Failure Modes
- Future Extensions

---

# Ontology Contribution Rules

Never duplicate concepts.

Before creating

- domain
- capability
- knowledge atom
- relationship

Search the ontology first.

Every ontology addition must include

- description
- relationships
- prerequisites
- examples
- references

---

# World Simulation Rules

Generated worlds should remain realistic.

Avoid

- impossible companies
- unrealistic architectures
- artificial incidents
- perfect software

Engineering worlds should contain

- uncertainty
- technical debt
- historical decisions
- conflicting priorities
- realistic failures

---

# Dataset Generation Rules

Every generated Engineering Knowledge Record should contain

- context
- objectives
- constraints
- reasoning
- implementation
- validation
- lessons
- references

Generated records should never consist solely of code.

---

# Quality Requirements

Every contribution should improve at least one of

- knowledge quality
- reasoning quality
- educational quality
- engineering realism
- maintainability
- dataset diversity

---

# Validation Requirements

No contribution may violate

- schema rules
- ontology rules
- graph integrity
- compiler architecture
- version compatibility

All validations must pass before merging.

---

# Testing Requirements

Every significant change should include

- validation tests
- regression tests
- ontology tests
- graph tests
- serialization tests

---

# AI Agent Contributions

TOON is designed to support AI-assisted development.

AI-generated contributions are welcome provided they satisfy the same quality requirements as human contributions.

Every AI-generated contribution must

- be reviewed
- be validated
- pass compiler checks
- preserve architecture
- remain explainable

Human review remains mandatory.

---

# Review Guidelines

Reviewers should evaluate

- correctness
- reasoning
- engineering value
- ontology consistency
- graph quality
- documentation
- maintainability

Reject changes that

- duplicate knowledge
- reduce quality
- increase ambiguity
- violate architecture
- introduce inconsistency

---

# Versioning

Every merged contribution should update

- documentation
- changelog
- version metadata
- affected specifications

Breaking changes require a major version increment.

---

# Community Expectations

Contributors are expected to

- respect differing opinions
- provide constructive feedback
- prioritize evidence over assumptions
- focus on engineering quality
- document significant decisions

The project values thoughtful discussion over rapid changes.

---

# Long-Term Goal

Every contribution should move the compiler closer to its ultimate objective:

> Building an evolving engineering knowledge system capable of generating datasets that teach machines how experienced engineers think, reason, design, build, debug, and continuously improve software systems.

Quality is measured not by the number of contributions, but by the engineering intelligence they add.
